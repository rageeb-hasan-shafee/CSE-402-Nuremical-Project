Base Paper & Problem Formulation

Base Research Paper: Tailin Zhu (2020), N-body Simulations of the Solar System with CPU-based Parallel Methods, School of Physics, University of Bristol.

The Numerical Task: Direct all-pairs gravitational integration of the Solar System (Sun, 8 planets, Moon) scaled up to tens of thousands of bodies using synthetic Main Asteroid Belt particles ($a \in [2.1, 3.3]\text{ AU}$).

Direct Gravitational Summation

a_p = ∑_{j ≠ p} G * m_j * (r_j - r_p) / (||r_j - r_p||² + ε²)^(3/2)

Units: Length in AU, Time in days, Mass in Solar Masses ($M_\odot$), $G = 2.9591220828559 \times 10^{-4}\text{ AU}^3 M_\odot^{-1}\text{ day}^{-2}$. Plummer softening $\epsilon = 0$ (point-mass Newtonian gravity).

Relativistic Extension (1PN Perihelion Precession)

Based on Tatekawa (2018), we incorporate the dominant 1st-order Post-Newtonian (1PN) General Relativity correction. This reproduces the historical textbook test of General Relativity:

  • Measured Mercury Precession: 42.983 arcsec/century
  • Analytic Einstein 1PN Prediction: 42.980 arcsec/century
  • Newtonian Baseline: 0.009 arcsec/century (closed ellipse, ~0 drift)

Velocity Verlet Symplectic Integrator

Why did Tailin Zhu (2020) and our project select Second-Order Velocity Verlet instead of Runge-Kutta 4 (RK4) or Euler?

1. Drift: $r_{k+1} = r_k + v_k \Delta t + \frac{1}{2} a_k \Delta t^2$

2. Force Evaluation: Recompute $a_{k+1} = a(r_{k+1})$

3. Kick: $v_{k+1} = v_k + \frac{1}{2} (a_k + a_{k+1}) \Delta t$

System Architecture & High-Performance Design

1. Structure-of-Arrays (SoA)

Instead of Body objects (`struct { x,y,z,m }`), particles are stored in contiguous parallel buffers (`vector x, y, z, m`). Allows CPU/GPU hardware prefetchers to stream 64-byte cache lines directly into AVX2/SIMD registers with 0% wasted memory bandwidth.

2. Zero Allocation in Inner Loop

Dynamic memory allocation (`malloc`, `new`, `std::vector::resize`) inside the simulation loop causes severe kernel thrashing. Buffer pointers (`ax`, `bx`) are allocated once during setup and swapped via $\mathcal{O}(1)$ pointer swaps at each time step.

3. Shared Contract v1 I/O

Strict standardization (`common/CONTRACT.md`) ensures all backends accept identical CLI parameters (`--input`, `--steps`, `--dt`, `--workers`, `--variant`) and output identical schema v1 telemetry JSONs, enabling automated verification via `bench/check_result.py`.

Supervisor Oral Defense Q&A Prep & Technical Cheat Sheet

Curated technical questions tailored for individual group members based on course evaluation requirements.

Q1: Why did you use Velocity Verlet instead of Euler or Runge-Kutta 4 (RK4)? NUMERICAL METHODS
Key Defense Answer: Velocity Verlet is a symplectic integrator. Hamiltonian systems preserve phase-space volume (Liouville's theorem). Standard non-symplectic integrators like Euler or RK4 continuously bleed or inject energy into orbital trajectories, causing planets to either spiral into the Sun or fly outward into space over thousands of orbits. Velocity Verlet keeps energy bounded in an exact oscillating band. Furthermore, Velocity Verlet requires only 1 force evaluation per time step (compared to 4 evaluations in RK4), making it $4\times$ faster while strictly conserving the Hamiltonian.
Q2: Why does OpenMP run SLOWER than single-core serial execution at N = 100? OPENMP / SCALING
Key Defense Answer: This empirical finding replicates Figure 4 of Tailin Zhu (2020). At $N=100$, the entire force calculation takes merely $\approx 0.035\text{ ms}$ on a modern CPU. The hardware overhead of spawning threads, synchronizing thread-pool barriers at `#pragma omp parallel`, and thread migration between CPU caches takes significantly longer than the actual floating-point math! Parallelization only delivers speedup when computational payload exceeds synchronization latency ($N \ge 500$).
Q3: Why does `dynamic` scheduling beat `static` on Intel i5-1340P, but not on AMD Ryzen? MICROARCHITECTURE
Key Defense Answer: Intel's 13th Gen i5-1340P is a hybrid asymmetric architecture with 4 fast Performance-cores and 8 slower Efficient-cores. Under `static` schedule, each thread receives an identical $N/P$ body chunk. The fast P-cores finish early and sit idle at the OpenMP barrier waiting for the E-cores to catch up. Under `dynamic` schedule with chunk size 16, P-cores consume chunks faster, balancing the asymmetric cores and achieving a $1.45\times$ speedup! In contrast, the AMD Ryzen 5 5600G has 6 identical symmetric Zen 3 cores, so static work-sharing is already balanced with zero chunk-scheduling overhead.
Q4: How does Newton's 3rd Law (`newton3`) cut floating-point operations by 50%? ALGORITHMS
Key Defense Answer: By Newton's third law, the force exerted by body $j$ on body $p$ is equal and opposite ($\vec{F}_{jp} = -\vec{F}_{pj}$). Instead of running an $N \times N$ double loop, `newton3` loops over pairs where $j > p$ ($\approx \frac{N(N-1)}{2}$ interactions), halving the number of distance calculations and square roots. To avoid data races between parallel threads updating the same body, each thread accumulates forces into thread-private buffers which are reduced at the end of the step.
Q5: How does Shared Memory Tiling accelerate CUDA GPU execution? CUDA GPU
Key Defense Answer: In naive CUDA N-body, every thread repeatedly fetches $N$ body coordinates from high-latency global GPU VRAM ($O(N^2)$ global memory transactions). In our `tiled` kernel, threads in a 256-thread block cooperatively load a tile of 256 bodies into ultra-fast on-chip `__shared__` memory (SRAM) with `__syncthreads()`. All 256 threads then calculate forces against this cached tile simultaneously. This cuts global VRAM bandwidth traffic by a factor of $B = 256\times$, eliminating the memory bus bottleneck.
Q6: Why is single-precision (FP32) so much faster than double-precision (FP64) on RTX 5090? HARDWARE ACCELERATION
Key Defense Answer: Consumer GeForce GPUs (including the RTX 5090) are engineered primarily for graphics, AI, and single-precision workloads, possessing a hardware FP64-to-FP32 ALU ratio of 1:64 or 1:32 (unlike data center chips like the NVIDIA A100 or H100 which have 1:2 FP64 ratios). Therefore, `tiled-f32` achieves up to **$28\times$ higher throughput** than `tiled-f64`, completing 10,000 bodies in just $0.556\text{ ms/step}$!
Q7: In MPI, what is the trade-off between `allgather` and `master-worker`? MPI / DISTRIBUTED
Key Defense Answer: In `allgather`, every rank owns $N/P$ bodies, updates their positions, and all ranks exchange their updated slices simultaneously via `MPI_Allgatherv`. In `master-worker`, rank 0 gathers all positions via `MPI_Gatherv` and then broadcasts the full state to all workers via `MPI_Bcast`. For high process counts, `master-worker` suffers from a communication bottleneck at rank 0, whereas `allgather` leverages decentralized parallel network topologies.
